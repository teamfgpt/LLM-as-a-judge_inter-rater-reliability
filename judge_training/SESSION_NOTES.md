Working notes from getting `judge_training/` from a documented-but-untested state to a
running ablation, plus what came out of the first real run. Read `README.md` first for the
overall design; this doc is the "what actually happened" log on top of it.

_Last updated: 2026-09-15 (evening) — completed the full 16-cell ablation and verified the
Gemma2 QLoRA repair. One partial-coverage result remains: Qwen2.5 English QLoRA has
12/129 unparsable test outputs; its metrics are based on 117 valid predictions._

## 1. Environment setup

- **GPU driver**: `nvidia-smi` was already healthy (driver 595.91.07, RTX 4070 Super) —
  the version-mismatch the README's §0 warns about had already resolved itself (likely an
  earlier reboot). No reboot was needed or done.
- **HF cache corruption**: every file in the HF cache's `snapshots/` dirs
  (`/data/dev/huggingface/hub`) was a 1067-byte `XSym` placeholder stub instead of a real
  symlink to the blob — classic USB-transfer-without-symlink-support damage. The blobs
  themselves (3.9–5.8GB each) were intact. Fixed by walking every `models--*/snapshots/`
  file and converting placeholder stubs back into real symlinks (49 fixed, 0 data loss, no
  re-download needed).
- **Ollama manifests missing**: `~/.ollama/models/blobs/` had all 4 model blobs
  (7.7–9.8GB) but `manifests/` was empty, so `ollama list` showed nothing. `ollama pull`
  for each of the 4 tags reused the existing local blobs by hash (seconds each, no
  re-download) and just rewrote the manifest.
- **Hardened `download_models.py --check`**: the old check only verified the snapshot
  *directory* existed, which is how the HF corruption above went undetected. Added
  `validate_snapshot()` — walks every file, flags broken symlinks, zero-byte files,
  unresolved placeholder stubs, and any `.safetensors`/`.bin`/`.gguf`/`.pt`/`.pth` file
  under 1MB (too small to be real weights). Verified it both passes on the real fixed
  cache and correctly flags a synthetic corrupted file.
- **`.venv_train` build**: system Python is 3.14 (too new for the cached torch cp313
  wheel). `uv` (`/data/dev/bin/uv`) already had Python 3.13.15 installed locally and a
  12GB wheel cache including `torch==2.11.0+cu126`. Rebuilt `.venv_train` on 3.13 and
  installed torch straight from cache (no re-download). Installed `unsloth` from current
  PyPI (2026.9.4) rather than the README's stale git+CUDA-extras command — modern unsloth
  auto-detects torch/CUDA and that install path is deprecated.
- **torchvision CUDA mismatch**: the resolver initially pulled a CUDA-13-tagged
  torchvision against the CUDA-12.6 torch, which crashed on import
  (`RuntimeError: ... different CUDA major versions`). Pinned to
  `torchvision==0.26.0+cu126` to match.
- **`check_unsloth.py`**: passes clean after the above — real forward pass on
  Qwen2.5-0.5B on the GPU confirmed working.

## 2. Wired up live training feedback (was previously silent)

Before this session, `train_qlora.py` had no `eval_dataset`, no live metrics beyond
`logging_steps=10` training-loss lines, and `val.jsonl` was generated by `data_prep.py`
but never read by anything. `run_ablation.sh` also fully redirected each run's stdout into
a per-run log file, so an unattended `nohup` run showed nothing live.

- Added a `ValQWKCallback` (`TrainerCallback`) in `train_qlora.py` that runs a real
  generation-based eval (reusing `eval_judge.py`'s scoring, not a mocked metric) against
  `val.jsonl` at the end of every epoch, prints an Ultralytics-style per-column QWK table,
  and appends one JSON line per epoch to
  `judge_training/logs/<model>-<lang>_val_metrics.jsonl`.
- Wired `eval_dataset=val_ds` + `eval_strategy="epoch"` into `SFTConfig` so `eval_loss` is
  also tracked per epoch (free from the Trainer, no extra generation cost).
- Refactored `eval_judge.py` to expose `evaluate_rows()` / `print_results()` as reusable
  functions — single source of truth for scoring, used by both the CLI and the new
  training callback.
- `run_ablation.sh`'s `run()` helper now `tee`s each run's output instead of a plain
  redirect, so progress bars and per-epoch tables are visible live in `_run_all.log`
  (and therefore in `nohup`'s output), not just buried in the per-run log.
- Validated the whole wiring with a real 1-epoch smoke run before trusting it on the full
  8–13h batch (temporarily set `epochs: 1` in `configs/models.json`, ran
  `qwen2.5-7b-instruct` / `id`, confirmed loss logs + per-epoch val QWK table + eval_loss +
  adapter save all worked, then reset to `epochs: 3` and discarded the test checkpoint).

## 3. Bugs found and fixed in the ablation code itself

- **`render_prompt()` crash on every few-shot call** (`eval_judge.py`): was doing
  `template.replace("{FEW_SHOT_EXAMPLES}", fewshot_block).format(**row)` — two passes.
  Because `fewshot_block` is raw `json.dumps(...)` output containing literal `{...}`
  braces (the SME label JSON), `.format()`'s second pass re-scanned those braces as format
  fields and crashed with `KeyError: '"relevance_label"'`. This is why **every one of the 8
  prompt-only runs from an earlier, unassisted attempt that same morning had failed
  identically** (see `logs/*-promptonly.log` timestamps ~07:14, before this session's
  fix). Fixed to a single `.format(FEW_SHOT_EXAMPLES=fewshot_block, **row)` call. Same
  latent pattern fixed in `train_qlora.py`'s `format_example()` for consistency (harmless
  there since it always passes `""`, but same bug shape).
  Validated live against Ollama (`qwen2.5:7b-instruct-q8_0`, `id`, fewshot=4) before
  trusting the full batch: 0 parse failures.
- **Missing `requests` dependency** in `.venv_dataprep` — `eval_judge.py`'s Ollama backend
  needs it; wasn't installed. Added.
- **Ollama VRAM collision at the Axis A → Axis B boundary**: Ollama's default 5-minute
  `keep_alive` left the last-used model tag resident in VRAM right as `run_ablation.sh`
  moved from the Ollama-backed prompt-only runs into the Unsloth QLoRA training runs. With
  ~8GB still held by Ollama, the first 2 QLoRA loads
  (`qwen2.5-7b-instruct-id`, `llama3.1-8b-instruct-id`) failed immediately with
  `ValueError: Some modules are dispatched on the CPU or the disk` (bnb 4-bit couldn't fit
  in the ~3.4GB actually free). Fixed live mid-run (`ollama stop <tag>` for the currently
  resident model) and added a permanent fix to `run_ablation.sh`: `ollama stop` for every
  pulled tag right before the Axis B loop starts, so future full reruns won't hit this.
  The 2 failed combos were re-run manually afterward once the GPU was confirmed free.

## 4. Gemma2-9B QLoRA — repaired and rerun successfully

- The original Gemma2 QLoRA runs were broken: both adapter runs showed 129/129 JSON parse
  failures. Gemma2's **prompt-only (Ollama)** results were unaffected and usable.

- **First patch attempt (earlier today) — necessary but not sufficient.** Marked Gemma2
  with `hf_prompt_format: "chat"` in `configs/models.json` so it trains/evaluates with its
  native `<start_of_turn>user` / `<start_of_turn>model` chat template instead of the raw
  `SYSTEM:/USER:/ASSISTANT:` transcript, on the theory that the wrong prompt format was
  the root cause. A retry (`gemma2-9b-it-id`, killed after epoch 1) still showed **130/130
  parse failures** — same symptom, so this wasn't the (whole) story.

- **Bug #1 found and fixed: double BOS token in `eval_judge.call_hf()`.**
  `format_hf_prompt()` builds the chat-format prompt via `tokenizer.apply_chat_template(...,
  tokenize=False)`, whose template already starts with `{{ bos_token }}` (confirmed by
  reading the saved `chat_template.jinja`). `call_hf()` then re-tokenized that string with
  `tokenizer(hf_prompt, ...)`, whose default `add_special_tokens=True` silently prepends a
  *second* BOS. Verified directly: token ids came out `[2, 2, 106, ...]` instead of
  `[2, 106, ...]`. This is a known, named gotcha — TRL's own `SFTTrainer` already guards
  against the identical issue for the *training* text (`trl/trainer/sft_trainer.py`:
  `add_special_tokens=False, # to avoid adding the BOS, twice`, citing
  https://huggingface.co/blog/qgallouedec/gotchas-in-tokenizer-behavior#7-chat-template-and-tokenization-dont-compose-due-to-special-tokens),
  but nothing guarded the eval/generation path. Fixed: `call_hf()` now passes
  `add_special_tokens=(prompt_format != "chat")`.
  **This alone did not fix Gemma2** (verified — see next point), but it's a real bug worth
  keeping fixed, and it's presumably why the earlier "even the base model produces empty
  output" test in this doc's previous revision still failed after just the template patch.

- **Bug #2 found — the actual root cause: Unsloth's Gemma2 fast-inference patch is broken
  in this environment.** Loaded the *base* (non-fine-tuned) `unsloth/gemma-2-9b-it-bnb-4bit`
  through `FastLanguageModel.from_pretrained` + `for_inference`, with the BOS fix applied,
  and generated on both the real task prompt and a trivial "Say hello in one word." prompt.
  Both immediately produced exactly one new token: `<eos>` (id 1) — confirmed with raw
  token ids, not just decoded text. The identical weights (`unsloth/gemma-2-9b-it-bnb-4bit`)
  loaded via **plain `transformers.AutoModelForCausalLM.from_pretrained`** (no Unsloth
  import at all) generate normally on the same prompt (`"Hello! <end_of_turn>"`). So this
  is not a prompt-format or fine-tuning problem — it's Unsloth's Gemma2 patch
  (`==((====))== Unsloth 2026.9.4: Fast Gemma2 patching. Transformers: 5.5.0.`) producing
  degenerate logits for every input, in this specific Unsloth/transformers version
  combination. (Tried `attn_implementation="eager"` as a lighter-weight fix first, since
  Gemma2's logit softcapping is sensitive to attention backend — Unsloth ignored the kwarg,
  config stayed `sdpa`, still broken. Full bypass was the only thing that worked.)

- **Fix implemented**: added a per-model `"backend"` field in `configs/models.json`.
  `gemma2-9b-it` now has `"backend": "transformers"`; the other 3 models are untouched
  (still default to `"unsloth"`, still have their existing valid results). `train_qlora.py`
  and `eval_judge.py` now branch on this: the `"transformers"` path loads via plain
  `AutoModelForCausalLM` + `BitsAndBytesConfig(4bit)` (new `eval_judge.load_plain_hf_base()`
  helper) and wraps LoRA via `peft.get_peft_model` + `prepare_model_for_kbit_training`
  instead of Unsloth's `FastLanguageModel.get_peft_model`. Deliberately does **not**
  `import unsloth` anywhere on this path, since Unsloth patches transformers' Gemma2
  modeling code at import time and that patch is the bug — importing it at all, even
  without calling `FastLanguageModel`, wasn't tested and isn't worth the risk of silently
  reintroducing the same degenerate output.
  - Side-effect fix needed to make this path work at all: the installed `trl==0.24.0`'s
    `SFTTrainer` no longer accepts the `tokenizer=` kwarg or `dataset_text_field=` /
    `max_seq_length=` directly on `SFTTrainer(...)` (renamed to `processing_class=` and
    moved into `SFTConfig` as `dataset_text_field` / `max_length`). The existing code only
    worked because **Unsloth patches `trl.SFTTrainer` at import time** to accept the old
    kwargs — a compatibility shim the plain-transformers path doesn't get. Updated
    `train_qlora.py` to use the current TRL API directly; re-verified this doesn't break
    the Unsloth-backed models either (see below), so this fix applies to all 4 models, not
    just Gemma2.
  - Side-effect fix #2: plain `peft`/`bitsandbytes` (no Unsloth memory optimizations) OOMs
    at the default `per_device_batch_size=2` on this 12GB card (confirmed — hit a real
    `CUDA out of memory` at ~9.5GB allocated). Added a per-model `train_overrides` block in
    `configs/models.json` for `gemma2-9b-it`: `per_device_batch_size: 1`,
    `gradient_accumulation_steps: 16` (same effective batch size of 16, per the README's own
    documented OOM fallback in §3). `load_config()` in `train_qlora.py` now merges
    `train_overrides` over the global `train` block per-model.
  - `ValQWKCallback` now takes a `backend` param and calls `model.eval()`/`model.train()`
    instead of `FastLanguageModel.for_inference/for_training` when backend is
    `"transformers"`.

- **Verified before the full rerun:**
  1. `eval_judge.call_hf()` on the *base* Gemma2 model via the new plain-transformers
     path produces a correctly parseable judge response (`{"relevance_label": 1, ...}`)
     for a real val-set row — confirms the generation bug is actually fixed, not just
     hidden.
  2. A tiny real training run (8 train rows, 3 val rows, 1 epoch, `per_device_batch_size=1`)
     through the full `train_qlora.py` code path (LoRA wrap → `SFTTrainer` → per-epoch
     `ValQWKCallback`) completed with **0/3 parse failures** and no OOM.
  3. Re-ran the same tiny-training smoke test through the **Unsloth** path (tiny
     Qwen2.5-0.5B) with the new TRL API to confirm the `processing_class`/`SFTConfig`
     change doesn't regress the other 3 models — it trained and evaluated cleanly (0/3
     parse failures there too).
- **Full rerun result:** `retry_gemma2_fix.sh` completed both 3-epoch runs. Validation had
  0/130 parse failures at every epoch for both languages, and the held-out test had 0/129
  parse failures for both `gemma2-9b-it-id-qlora` and `gemma2-9b-it-en-qlora`.
- `summarize_results.py` now restricts `_comparison.csv` to the configured 2x4x2 grid and
  reports ignored non-grid result files, so stale artifacts like the older
  `qwen2.5-7b-id-promptonly.json` no longer appear as a 17th experiment row.

**id-vs-en gap (README §3b, §7), now answered — and it's not consistent across models.**

direction) is model-dependent. Worth flagging before drawing a general conclusion about
Indonesian-language judge quality — it may be more about per-model id pretraining/tokenizer
coverage than a property of the task itself.

## Session Summary: 2026-09-22 (Phase 2 Active Learning Extraction)
### 1. The "Data Starvation" Issue
- Discovered that the fine-tuned base models were severely overfitting due to an extremely small validation set (only 8 unique signals).
- Alternative models (Prometheus-2-7B, SeaLLM-v3-7B-Chat) failed to generalize on the ID holdout set, producing worse QWK scores.
- Attempted to use deepseek-v4-flash via a proxy API, but failed due to aggressive WAF blocking (401/400 errors). Decided to stick with local models.

### 2. Phase 2 Active Learning Implementation
- To fix the structural overfitting, we initiated Phase 2 of the Master Plan: AI-Assisted Sampling.
- Found the raw pipeline dataset `job_context_candidate_review_pool.csv` containing ~366k rows (274k unlabeled).
- Extracted exactly **1,000 diverse samples**, each from a unique `competency_signal_id`, to maximize task coverage and diversity.
- Ran mass inference on these 1,000 rows using our best Indonesian model (`Llama-3.1-8B-Instruct-ID` checkpoint-120).
- Outputted the AI-predicted labels and rationales to `SME_SAMPLING_SHEET_PHASE2_DIVERSE.xlsx` for SME review.

### 3. Inter-Rater Reliability (IRR) Strategy for SME Review
- For the upcoming expert review of these 1,000 rows, we established the evaluation metrics:
  - **Quadratic Weighted Kappa (QWK):** The primary metric (as established in previous phases) for measuring agreement on ordinal scales (e.g., 0, 1, 2 for relevance), heavily penalizing polar disagreements. Ideal for exactly 2 raters.
  - **Krippendorff's Alpha / Fleiss' Kappa:** To be used if 3 or more SMEs are reviewing, as Cohen's/Weighted Kappa is limited to two raters. Krippendorff's Alpha is preferred for ordinal data robustness.

### 4. SME Rating Web Portal (Preparation for Dissertation Phase)
- Designed a custom **Streamlit Web Application** (`sme_web_app/app.py`) to facilitate a seamless inter-rater reliability test for 2 expert raters.
- The app uses the 3-point ordinal scale (2: Agree, 1: Partially Agree, 0: Disagree).
- Goal: If the IRR (measured by QWK) meets the standard, this perfectly fine-tuned model will proceed to **Mass Inference**, scoring hundreds of thousands of rows to establish a complete dataset for the next phase of the dissertation.

### 5. Dissertation Literature Support (Methodology Foundation)
- Established the theoretical justification for the **3-Point Ordinal Scale (0, 1, 2)** to reduce cognitive load and grade semantic relevance.
  - *Jacoby, J., & Matell, M. S. (1971). Three-point Likert scales are good enough.*
  - *Järvelin, K., & Kekäläinen, J. (2002). Cumulated gain-based evaluation of IR techniques.*
- Established the theoretical justification for **Quadratic Weighted Kappa (QWK)** as the primary inter-rater reliability metric for ordinal data.
  - *Cohen, J. (1968). Weighted kappa: Nominal scale agreement provision for scaled disagreement or partial credit.*
  - *Zheng, L., et al. (2023). Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena.*
- **Next Milestone:** Await the completion of the SME rating via the `sme_web_app`. If the QWK score achieves the baseline (e.g., >0.6), the AI will proceed to Mass Inference (Phase 4) on all 366k+ rows.
